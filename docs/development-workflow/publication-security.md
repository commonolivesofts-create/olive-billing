# Mandatory public-repository publication gate

Company authorized public source code and sanitized technical documentation on 28 November 2026. Actual secrets, customer/business records, private infrastructure and internal operations are excluded. This standard applies to both developers and every future change, including docs, fixtures, migrations, tests, CI and release artifacts.

## Classify before publishing
Public: approved scope, generic architecture, endpoint contracts, schema and security design, synthetic examples and variable names. Private: actual hostnames/IPs, deployment topology/operational thresholds, personal contact details, production IDs, credentials, real customer/invoice records, internal runbooks and scan reports. Standard security mechanisms are not secrets and must not rely on obscurity. Use environment references and reserved example domains. Keep original private source requirements in access-controlled storage, not Git.

## Configure safely
Copy server/client `.env.example` to ignored local `.env` only when the corresponding implementation is authorized. Server configuration is validated at startup; fail closed on missing secrets, never default production secrets. Production uses a protected secret manager or access-controlled environment injection. Distinct environment and migration credentials; rotate separately. Use interactive admin password provisioning, Argon2id hashes in the database; no persisted plaintext user/admin password. SMTP settings managed by the approved UI store an encrypted secret or protected secret reference; never return it. Optional provider secrets are server-only. Do not introduce JWT. No secret in `VITE_*`, client bundles, public source maps, API errors/responses, browser storage or logs. Session cookie is HttpOnly; CSRF token is held in memory. Redact Pino and audit data. Test these guarantees when code exists.

## Before commit and push
1. Review `git status --short --untracked-files=all`, `git diff`, `git diff --cached`, file names, staged snapshot and all relevant source/config/docs. Review binaries separately; no real data. Review public Git author metadata and use approved email settings for future commits if needed.
2. Run `git check-ignore -v --no-index` against representative forbidden paths and verify both exact `.env.example` files are allowed. Run `git ls-files -ci --exclude-standard` to identify tracked files now ignored. Stop if any sensitive files are tracked; ignoring is not untracking.
3. Fetch authorized remote refs, verify history and branches, run Gitleaks locally: `gitleaks git --redact --log-opts="--all --reflog" .`, `gitleaks git --staged --redact .`, `gitleaks dir --redact .`. Run from repository root, with a verified official scanner and no reports committed. Review nonzero exit codes; scanner findings need secure triage. Directory scans may include ignored private files; do not share values or reports. Review all reachable and reflog history; no tool can prove that old remote caches/forks never contained secrets.
4. Inspect built frontend and source maps when available, verify only explicitly allowed public configuration is exposed, and test API/log/browser behavior. Until implemented mark not applicable, not passed.
5. Obtain owner approval for the staged content and redacted scan summary before commit. Re-run verification before push; require independent PR review and CI secret scanning/branch protections when configured. Do not bypass a failed scan or push protection.

## Incident handling
Stop publication. If real credentials are exposed, revoke/rotate immediately, assess usage and affected systems, notify authorized security owner. If only locally committed, amend or otherwise replace unpublished history after approval; merely adding a cleanup commit leaves old content reachable. If remotely published, coordinate history cleanup, collaborators, forks/caches and GitHub Support as appropriate; never force-push without explicit authorization. Document sanitized evidence privately. No scan guarantees absence of all confidential data. Broad document/export ignore rules are intentional: allow a specific synthetic fixture only after separate review, never unignore a whole private file class.

## Private runbook
`README.private.md` is ignored at any depth. Create only after testing the ignore rule. Keep access-controlled, share via company-approved private storage/password manager; never put live passwords in the runbook. Do not use public PRs, issues or chats for secrets. Private material is not automatically shared by Git.
